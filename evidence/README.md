# Evidence

Everything here was produced by the code in this repository against the local AcmeCore mock bank (fictional, synthetic data). Every file passed `scripts/audit_evidence.py`: no secrets, none of the mock's synthetic PII (names, SSNs, dates of birth, addresses, phones, member numbers), no dollar amounts. Screenshots are masked at capture time (see the masking bug found in final review, below). `runs/` is git-ignored; this folder holds curated copies.

## 1. Discovery with a real model (Claude Opus 5)

| Run | Goal (typed with a concrete member number; the evidence stores it as `{{member_number}}`) | Result |
|---|---|---|
| [`01-read-flow`](discovery/01-read-flow/) | "Look up member {{member_number}} and read their current savings balance and their list of shares" | 7 model turns. Compiled `acmecore.member.get_savings_balance_and_shares@1.0.0` (5 steps), verified by replay on a different member. |
| [`02-write-flow`](discovery/02-write-flow/) | "Open a new {{share_product}} share for member {{member_number}} with an initial deposit of {{initial_deposit}} and the nickname {{nickname}}, and return the confirmation number and the new share ID" (typed as Holiday Club, 250.00, Gift fund) | 12 model turns. At *Confirm* the run asked for approval and a person approved it in the operator console ([`interventions/`](discovery/02-write-flow/interventions/)). Compiled `acmecore.share.open_share_account@1.0.0` (11 steps). Verification on a different member asked for, and got, its own approval, and committed. |

In each run folder:
- `goal_spec.yaml`: the typed spec the goal compiler produced (inputs, outputs, sensitivity).
- `events.jsonl`: every model turn (model, usage, the summarized thinking as the "why"), every decision and its reason, each grounded step, detectors, approvals, compile and verify results. All redacted.
- `screenshots/` and `snapshots/`: exactly what the model saw each turn, masked, with ref marks. The write flow's screenshots were removed (see below); its redacted text snapshots remain.
- `trace.json`: the grounded steps with the validated strategies of every element acted on.
- `capability.yaml`: the artifact as saved (then approved in `capabilities/`); `discovery_report.json`; `verify-by-replay/`.

Worth noticing in the logs: in the read flow the model's first attempt to bind the shares table used the wrong column names; the tool rejected it with the table's real headers and the model corrected itself on the next turn. In the write flow the model noted the member already had a Holiday Club share before going ahead. Prompt caching kept input cost low: the read flow read about 51k tokens from cache and wrote 11k; the write flow read about 372k and wrote 56k.

Kept exactly as discovered, for a reviewer to judge: the goal asked for both a share *type* and a *description*, and the table has one *Description* column, so the model mapped both outputs to it. The goal compiler named the write capability `acmecore.share.open_share_account` with input `share_product`; the compiler narrowed that input's allowed values to what the dropdown offered.

## 2. Deterministic replay, no model

[`replay/SUMMARY.md`](replay/SUMMARY.md) lists the 15 scenarios, generated by `scripts/generate_evidence.py` from the two discovered, approved capabilities:

- **Business outcomes**: member not found, restricted account, a member with no savings row.
- **Rejections before touching the UI**: bad input, an unapproved artifact on a production tenant.
- **Recoveries**: maintenance pop-up, session timeout.
- **Hard failures**: persistent server error, unknown pop-up, vendor drift.
- **Cross-tenant success** with the approved version overlay.
- **Commits**: parked for approval; approved and committed; response lost, which reports `side_effect: unknown` and is never retried.

Each scenario ran twice from a freshly reset bank and matched on status, code, side effect, recoveries, warnings, outputs and the step-path hash. The hash covers only the path (steps, how each ended, which locator matched), so scenarios that stop at the same step share it.

Each folder holds `result.json` (the result contract: status, outputs or outcome or error, `side_effect`, `retry_safe`, recoveries, warnings, interventions, per-step report) and `events.jsonl`. Failures add a masked screenshot and a redacted snapshot of the page where they stopped.

## 3. A person on the live session

Real people, real browser, same session:
- [`handoff/01-supervisor-pin`](handoff/01-supervisor-pin/): a $7,500 deposit exceeds the teller limit, so the app demands a supervisor PIN.
  1. Replay escalates.
  2. A person takes control of the same browser window, types the PIN (never captured) and approves.
  3. They hand back.
  4. Replay re-checks the receipt page, reads the confirmation number and reports `committed`.
- [`handoff/02-deadline-passed-commit-found`](handoff/02-deadline-passed-commit-found/): the person entered the PIN and approved, but did not hand back before the 15-minute deadline. Replay looked at the page, found the receipt, and reported `needs_human` with `side_effect: committed`, `retry_safe: false`. It did not claim that nothing happened.
- [`handoff/03-left-the-result-page`](handoff/03-left-the-result-page/): the person approved, then navigated away before handing back. Replay could not verify the commit, so it reported `side_effect: unknown`, `retry_safe: false`, with every human action recorded. This run led to the console's "STEP COMPLETE: hand control back now" prompt.

In every run the person's clicks and changes are in `events.jsonl` and `interventions/`, with values typed into secret fields recorded as `<not captured: secret field>`.

## 4. An agent invoking a capability by name

[`catalog/01-agent-question`](catalog/01-agent-question/): "What is the savings balance for member {{member_number}}, and which shares do they have?" (asked with a concrete number) The calling agent (Claude) saw the approved capabilities as strict tools generated from their contracts (`catalog.json`), called `acmecore__member__get_savings_balance_and_shares`, and answered from the typed result. The call itself was a deterministic replay ([`replay/`](catalog/01-agent-question/replay/)); the model was never in the execution path. The logged answer is redacted.

## A masking bug found in final review (fixed)

The runs with a person in the loop (the write-flow discovery, its verification, and the three handovers) used a visible browser window on a 2x (Retina) display.

- **What went wrong.** Values that share a line of text with other words ("Operator: …", a member number in a table cell) are painted over using boxes measured in CSS pixels. On a 2x screenshot those boxes landed in the wrong place. Cells masked by CSS (balances, PIN) were fine.
- **What was exposed.** In those screenshots the synthetic operator id, member number, share type and nickname were visible, including in the screenshots the model saw during the write-flow discovery. Its text observations were redacted as designed.
- **The fix.** Screenshots are now taken at CSS scale, and `tests/integration/test_masking.py` emulates a 2x display (it fails without the fix).
- **The evidence.** The affected screenshots were removed from this folder; each affected `screenshots/` folder has a `REMOVED.md`. Event logs, redacted snapshots and results are unchanged. All values involved are fictional.

## Not included, on purpose

- No Playwright traces: they store typed values (the password, the PIN) and cookies.
- No screen recording: raw video cannot be masked. The masked screenshots and event logs cover the same ground.
